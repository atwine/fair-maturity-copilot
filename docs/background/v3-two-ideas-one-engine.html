One engine, two applications

The FAIR maturity tool and the OMOP data-quality translator turned out to be the same underlying build, aimed at two different technical standards. That's not a coincidence worth ignoring — it's a sequencing advantage.

#3 FAIR maturity — build first #4 OMOP data-quality translator — build second #1 Luganda health MT — parked until eval work finishes #2 grant copilot — dropped, adoption risk

The shared engine: a "standard-to-plain-language" copilot

Both #3 and #4 take a dense, expert-built technical framework — the RDA's 41 FAIR indicators, or OHDSI's 3,300+ automated data-quality checks — and a non-technical stakeholder who's supposed to act on it but can't parse the output. Both need the same three-stage core: run the checks → score/structure the findings → have an LLM turn each finding into a plain-language "what's wrong and what to do" step. Build that core once against #3, where it's easiest to test (no database dependency, just a guided questionnaire), then point the same core at #4's OMOP output once there's real OMOP CDM data to run it against.

structured findings in→ severity scoring→ LLM remediation writer→ plain-language report out
Build order

Two ideas, sequenced

3. Guided FAIR data maturity assessment and remediation tool

build first

Walk a research group or health-data holder through the RDA FAIR Data Maturity Model in plain language, score it, then have Llama 3.3 turn each weak indicator into a specific, actionable fix. No external data dependency — you can build and test this entirely against ACE's own data practices.

It's self-contained: a questionnaire, a scoring rubric, an LLM remediation step. No waiting on TASO's data access or ETL decisions to start.
F-UJI automates 16 of 41 RDA indicators but reads as expert-only output — nothing wraps it (or the 25 manual indicators) in a guided, plain-language flow.
  1. Pick the 10-12 RDA indicators most relevant to a health-data-holding research center.
  2. Build the guided questionnaire + scoring rubric (a simple web form is enough for v0).
  3. Build the "structured findings → plain-language remediation" engine as its own reusable module, not hardcoded to FAIR — this is the piece #4 will reuse.
  4. Run it on ACE's own data practices as the first real test.
Source: RDA FAIR Data Maturity Model, Data Science Journal, 2020

4. A plain-language translator for OMOP CDM data-quality reports

build second

OHDSI's own Data Quality Dashboard already runs 3,300+ automated checks against an OMOP CDM database — the checking engine isn't the gap. The gap is that its output is an R-generated technical report built for informaticists. Point stage 3 of the shared engine (the plain-language remediation writer) at DQD's output instead of FAIR's, and TASO's data team gets a report they can actually act on.

It needs an actual OMOP CDM database to run against — which depends on your team's still-open decision on TASO's source system and ETL path. Building the remediation engine against #3 first means #4 is mostly wiring, not new design, once that data exists.
Building a new ETL engine. Several OpenMRS→OMOP ETL attempts already exist (jayasanka-sack/openmrs-to-omop, Hephaestus) and a full harmonization platform already exists pan-continentally (INSPIRE datahub). Whatever ETL path your team picks, this tool starts downstream of it, at the OMOP database.
  1. Run OHDSI's Achilles + Data Quality Dashboard against it to get the raw structured findings.
  2. Feed those findings into the remediation engine built for #3, adapting only the input parser and severity mapping.
  3. Pilot the plain-language report with TASO's actual data staff and revise based on what still doesn't land.
Sources: OHDSI Data Quality Dashboard · OHDSI Achilles · INSPIRE datahub, Frontiers in Digital Health, 2024
#1, Luganda health-domain MT — still the strongest idea on paper (existing models, existing eval set, a live fine-tuning plan, a team with a track record in this exact area), but you're mid-way through a real data effort: 10,000+ curated pairs being finalized, 1,000 already through third-party evaluation. Revisit once that evaluation lands — the two-week plan from v2 still applies, it's just not this month's build.

Net result: you're not choosing between two unrelated ideas — you're building one reusable "make a technical standard usable by a non-expert" engine, and applying it twice. That's a stronger GitHub story than two disconnected repos: the second release ships faster because the first one already did the hard design work, and the pattern itself (plain-language layer over a rigid technical checklist) is something you could point at other standards later if it lands well.
