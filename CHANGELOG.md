### Fixed
- **Empty LLM replies (mentor and remediation) when OpenRouter's `openrouter/auto` router picked a reasoning model.** A reasoning model spends completion tokens on invisible "thinking" before writing any visible answer; this app's token budgets (originally 300/400/700, sized against vLLM's plain model) could be entirely consumed by that hidden reasoning, producing `finish_reason: "length"` and a completely empty visible reply — not an error, just silence. Reproduced live twice: once on the mentor (`openrouter/auto` → `deepseek/deepseek-v4-flash-0731`, 2 of 3 test turns), once on a remediation prompt for a specific indicator even after budgets were first raised to 1200 (same model spent 900-1200+ tokens reasoning on that prompt alone, 2 of 3 attempts). No fixed budget is safe against an auto-router that can hand any request to a different reasoning model at any time, so `generate()`/`generate_chat()` (`backend/app/engine/llm_client.py`) now retry once with a much larger budget (4000) whenever they see the exact empty-reply-plus-`finish_reason:"length"` signature, instead of guessing ever-bigger fixed caps. Verified: the previously-failing remediation prompt succeeded 5/5 on repeated retries after the fix. See `docs/DECISIONS.md` v26.
- `frontend/app/icon.svg` and `assets/logo.svg`'s hand-written comments used a `--` dash (this project's normal prose style), which is invalid anywhere inside an XML/HTML comment body except at its very end -- Chrome rejected the favicon outright with a parse error. Caught by opening `/icon.svg` live in the browser, not by reading the markup. See `docs/DECISIONS.md` v24.
- **The Alembic baseline migration never created any tables.** Caught while preparing to promote toward production: `fd7648a1773b`'s `upgrade()` was a bare `pass`, written against a database that already had every core table from the pre-Alembic workflow -- running the full migration chain against a genuinely fresh database (what a real deploy needs) would create only the mentor/plan tables and fail on the next migration's foreign keys into tables that were never created. Reproduced against a real disposable Neon branch forked from the untouched "production" branch, fixed by generating the correct baseline DDL via autogenerate against the pre-mentor-POC model set, and verified end to end against a second fresh branch (all 12 tables created successfully). Also added a row-count safety guard to `b9aa2d13f2f5`'s `DELETE FROM mentorconversation/mentormessage` (flagged by three independent review passes as a real risk once headed toward a shared database) and fixed an unescaped `%` in `alembic/env.py`'s database URL handling that could break every future `alembic` invocation. See `docs/DECISIONS.md` v23.
- The mentor's `UPDATE_ANSWER:` parser required nothing after the confirmed value on that line; real vLLM output sometimes tacks the note onto the same line with an extra `|` instead of a separate `NOTE:` line, which made the whole line fail to match -- the raw marker leaked into the chat and no answer update happened. Caught testing issue #9 against live model output, not by the unit tests. See `docs/DECISIONS.md` v22.
- Plan and mentor chat pages had no way to start a new assessment — only the report page had a "Start another assessment" button, so a user done with either the plan or a mentor conversation had no path back to the start. Both now have the same button, linking to `/assessments/new`. Fixes [#10](https://github.com/atwine/fair-maturity-copilot/issues/10).
- `build_fairification_plan` couldn't distinguish "no open findings" from "the model's response didn't parse into any steps" — both returned an empty `Plan.steps`, which the frontend rendered identically as a false "you're all clean" message even when the goal text above it described real work still needed. Caught in self-review; a dedicated `PlanGenerationFailed` now surfaces the parse-failure case as a retryable 503 instead.
- `_rescore_finding_and_refresh_report` (the revisit-and-update path above) initially let an LLM/network failure during remediation regeneration propagate into a 500 on the whole answer-save request — even though the answer itself had already committed successfully. Caught in self-review before merge; the answer save and severity update are no longer at risk from a failed remediation call, which is now wrapped as best-effort.
- Shared a `remediation_by_finding_id` lookup helper between report generation and the new revisit path, and in doing so caught a latent key-type mismatch: `build_report_markdown` looks up drafts by `str(finding.id)`, but the dict being built used the raw `UUID` as the key, which would have silently produced remediation-less markdown wherever this helper was reused. Fixed before it was ever wired up.
- `FairSpectrum`'s segment-fill math assumed each FAIR principle's questions occupy one contiguous block in display order. The real order isn't contiguous — the "flex slot" Findable indicator (F3) sits last, after all four Reusable questions — so the Findable segment showed 100% filled after just the first 4 questions were answered, then stayed stuck there for the rest of the wizard while the true last Findable question went unanswered. Caught in self-review before merging; fixed by counting each group's filled members directly by index rather than by cumulative offset.
- **`globals.css`'s `--font-sans` was a circular self-reference** (`var(--font-sans)`), so it resolved to nothing and every page silently fell back to the browser's default serif (Times New Roman) instead of the Geist font actually loaded in `layout.tsx`. Found via a `design-critique` pass, not visible from the code alone — it read as a font *choice*, not a bug, until computed styles were checked directly.
- Default/sm/lg button sizes computed to ~28-36px tall — under the 44px WCAG touch-target minimum, with sm's text at 12.8px. Bumped across the size scale (`components/ui/button.tsx`).
- The selected-answer highlight in the question wizard was a single-pixel border-color change — too subtle to register at a glance. Now a 2px border plus a subtle fill tint and bold label on the selected option.
- **Report-generation race condition** — two concurrent `GET /report` calls for the same run (surfaced by React 19 Strict Mode's double effect invocation, but reproducible by any double-click or refresh mid-generation) each ran a full LLM generation pass, producing duplicate `Report`/`Finding` rows. Fixed with database-level unique constraints (`Answer`/`Finding` on `(run_id, indicator_id)`, `Report` on `run_id`) plus a wait-and-retry path so the losing request returns the winner's result instead of erroring or duplicating. `routes_answers.py`'s answer upsert had the same unprotected check-then-insert pattern and got the same fix pre-emptively. Verified with a real concurrent-HTTP regression test, not just sequential calls. See `docs/DECISIONS.md`.
- `_load_report_out` picked an arbitrary `RemediationDraft` per finding with no defined order when more than one existed (e.g. after a regenerate call) — could silently show a stale suggestion instead of the latest. Now explicitly ordered by `generated_at`.
- Banned-jargon regex in the remediation grounding check (`backend/app/engine/remediation.py`) was missing a word-boundary on its RDA-code branch, which could reject valid remediation text that merely contained an RDA-code-like substring inside a longer word. Caught in review before merging to `main`.
- `indicators.yaml`'s unquoted `yes`/`no` keys and values were silently parsed as Python booleans by PyYAML (the classic YAML 1.1 "Norway problem"), breaking every scoring lookup. Caught by actually running the tests, not by review.
- `scripts/seed_indicators.py` raised `DetachedInstanceError` when logging its success message, from reading an ORM attribute after the database session that loaded it had already closed.
- `content.py`'s YAML anchors/aliases meant every indicator sharing the default scoring rubric or answer options pointed at the exact same Python dict/list object rather than a copy — a latent shared-mutable-state bug. Now deep-copied per indicator; the YAML file is also now parsed once and cached instead of being re-read by three separate functions.
- The remediation grounding check rejected correct "who to ask" responses for `dont_know` answers with thin notes, since those legitimately don't share words with a near-empty note. Found live against real vLLM output during the Checkpoint 3 demo run; `dont_know` answers now bypass the reference-overlap check (word-count and jargon checks still apply).
- `scripts/run_demo_assessment.py`'s docstring said the tool defaults to local Ollama, written before the LLM default switch below — caught in review, updated to match.
- `routes_report.py`'s report generation raised an unguarded `KeyError` (opaque 500) if the database's `Indicator` table hadn't been seeded yet — now a clear error naming `scripts/seed_indicators.py`. Caught in review; regression test added.

### Changed
- **The mentor's confirmed-fix action now goes through a real tool call, not a text marker (issue #15).** `mentor.py` no longer regex-matches `UPDATE_ANSWER:`/`NOTE:` lines out of the model's free-text reply — a real `confirm_indicator_fix` tool (with a `reply_to_user` argument carrying the model's conversational reply, so this stays one LLM call per turn) is declared and passed via `tool_choice="auto"`. This had been deliberately avoided originally over concern that self-hosted vLLM might not have tool-calling enabled — checked directly against ACE's real vLLM endpoint and the OpenRouter fallback model, both confirmed to return correct structured tool calls, before building this. `llm_client.py` gained `generate_chat_with_tools()`; `mentor_system.jinja` rewritten to describe the tool instead of the marker format, `MENTOR_PROMPT_VERSION` bumped to `fair-mentor-v4`. Verified live: all 7 `test_mentor_live.py` tests pass against real vLLM, full suite 60/60. See `docs/DECISIONS.md` v29.
- **README's "LLM provider" section now has real, measured cost numbers (issue #19), not estimates.** Instrumented a full live flow (report + plan + a 3-message mentor conversation, one message triggering a re-score) against real vLLM to count actual tokens sent/received: 14,203 prompt / 852 completion across 18 calls. Applied to three providers' current listed prices: self-hosted vLLM ($0 marginal), the same Llama 3.3 70B hosted on OpenRouter (≈$0.002 for that flow), and Claude Sonnet 5 as a frontier comparison (≈$0.037, ~20x pricier). Documented that mentor conversations cost more the longer they run (every turn resends the full history) while report/plan cost is fixed per assessment, plus a multi-site cost extrapolation relevant to the consortium work (issues #16/#17) — even at frontier pricing, 11 sites stays under 50 cents total. See `docs/DECISIONS.md` v28.
- **LLM default reverted from OpenRouter back to self-hosted vLLM, and `openrouter/auto` dropped everywhere.** After a brainstorming session that surfaced a real, near-term multi-site consortium use case, the project owner decided the reliability problems already seen with OpenRouter's auto router (see the `[Unreleased] → Fixed` empty-reply entry below, and `docs/DECISIONS.md` v27) outweighed the modest speed/cost benefit — especially for higher-stakes, multi-organization work. `backend/.env` and `backend/.env.example` now default to vLLM (self-hosted, `ibnzterrell/Meta-Llama-3.3-70B-Instruct-AWQ-INT4`) again; OpenRouter remains available as a fallback, but pinned to a specific named model (`meta-llama/llama-3.3-70b-instruct` — the same model vLLM runs, so a fallback doesn't also mean a behavior change) instead of `openrouter/auto`. `README.md`'s "LLM provider" table and `backend/app/config.py`'s comments updated to match. Verified live against the real vLLM endpoint once network access allowed it: full backend suite, including all 18 live-LLM tests (report/plan/mentor), 61/61 passing. Tracked in [issue #14](https://github.com/atwine/fair-maturity-copilot/issues/14). See `docs/DECISIONS.md` v27.
- `Adapter.render_remediation_prompt` (`engine/ports.py`) gained a required `severity` parameter — every future adapter (e.g. the parked OMOP one) must pick its framing (fix vs. affirmation) based on it, same as `FairAdapter` now does. `POST /assessments/{id}/findings/{indicator_id}/regenerate` no longer rejects passing findings with a 400 — they have real content to regenerate now too.
- Repo default branch renamed `master` → `main`; adopted the full three-tier branching structure — `feature/<name>` → `development` → `staging` → `main`, with `main` reachable only via a reviewed, explicitly-approved PR (see `README.md`'s "Branching convention"). An initial two-tier version of this fix (feature → main directly) was corrected in the same session after review.
- `ROADMAP.md`'s v0 milestones reframed from calendar-day estimates to checkpoints — the original day-based plan assumed unassisted solo development, which doesn't match the actual Claude-assisted pace.
- Added a synthetic demo dataset checkpoint (`ROADMAP.md` Checkpoint 3) ahead of the API/frontend work — real ACE/TASO data, especially anything OMOP-shaped, likely needs a cleared data-governance path before touching any LLM, so the tool needs to be demoable and testable on fake data first.
- **LLM default switched from local Ollama to vLLM** (`app/config.py`, `.env.example`) — the Checkpoint 3 demo run showed Ollama was far slower in practice on available hardware, and vLLM is both dedicated A100 infra and the actual production target. Ollama kept as an offline fallback only.
