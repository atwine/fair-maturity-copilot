# Roadmap

This project is one reusable engine (`intake → scoring → LLM remediation writer → report`) applied to more than one technical standard, one adapter at a time.

**A note on timelines:** the original plan (`docs/PLANNING_PROMPT.md` output) estimated work in developer-days, assuming solo, unassisted implementation. In practice, with Claude doing most of the actual writing, a "day" of that plan can take a fraction of a working session — the first checkpoint below took well under a day. Below is tracked as **checkpoints**, not calendar days; how fast they land depends on session time and review turnaround, not headcount-style estimation. The detailed technical plan each checkpoint follows still lives in the approved plan file referenced in `devlog/HANDOFF.md`.

## v0 — FAIR data maturity adapter — **in progress**

Guided self-assessment against a subset of the RDA's 41 FAIR indicators, with LLM-generated plain-language remediation for each weak indicator.

- [x] **Checkpoint 1 — engine scaffold + boundary proof.** FastAPI app, SQLModel data model, the `Adapter` Protocol seam, an OpenAI-compatible LLM client, remediation grounding checks. Proven with a fake adapter before any FAIR content exists (`backend/tests/engine/test_boundary.py`, passing).
- [x] **Checkpoint 2 — FAIR adapter content.** `indicators.yaml` (the 12 selected RDA indicators, flex-slot resolved to F3-01M — see `docs/DECISIONS.md`), `FairAdapter.score()`, `scripts/seed_indicators.py`. Tested against SQLite (no Neon project yet) — seed script confirmed idempotent on a second run.
- [x] **Checkpoint 3 — synthetic demo dataset(s) + remediation writer live.** 4 fake dataset profiles (`backend/fixtures/synthetic_datasets.py`) varying in size/format/domain and FAIR maturity, run end-to-end through the real engine and a real LLM via `scripts/run_demo_assessment.py`. Pulled the remediation prompt template forward from its original later slot, since a real demo needed real remediation text — see `backend/app/adapters/fair/prompts/remediation.jinja`. Full reports in `docs/demo_reports/`. Scores ranged 6.2–68.8/100, proving the tool's actual range, not just one score. **LLM default switched from local Ollama to vLLM** after this run — Ollama was far slower in practice on this hardware, and vLLM is dedicated A100 infra and the actual production target anyway; Ollama stays as an offline fallback only.
- [x] **Checkpoint 4 — backend REST API.** `POST/GET /assessments`, `PUT /assessments/{id}/answers/{indicator_id}`, `POST /assessments/{id}/complete`, `GET /assessments/{id}/report` (generates once, caches — no re-calling the LLM on repeat views), `POST /assessments/{id}/findings/{indicator_id}/regenerate`, `GET /adapters/{id}/questions`. The `Adapter` Protocol was extended with `render_remediation_prompt`/`prompt_version` so the API layer never imports FAIR-specific code directly — it only knows `app/adapters/registry.py`, which is the one place that maps `adapter_id` to a concrete adapter. 32 tests total, including a live run against vLLM (report generation, caching behavior, and the regenerate endpoint all confirmed against the real model, not mocked).
- [x] **Checkpoint 5 — Next.js frontend.** Scaffold (Next.js 16 + React 19 + Tailwind v4 + shadcn/ui on Base UI), the 4-screen wizard (new → question → review → report) against the API contract. Full flow walked in a real browser via the Claude in Chrome extension, including editing a previously-answered question (pre-fill required a small backend addition — `AssessmentOut` now returns full answers, not just answered IDs). A real bug surfaced live: React 19 Strict Mode's double effect invocation fired two concurrent `GET /report` calls, exposing a report-generation race condition with no server-side protection — 2 `Report` rows and 24 `Finding`s for a 12-indicator run. Fixed with unique constraints (`Answer`/`Finding` on `(run_id, indicator_id)`, `Report` on `run_id`) plus a wait-and-retry path for the losing request, verified three ways: a direct-function race, a real concurrent-HTTP test, and a clean re-run in the browser. See `docs/DECISIONS.md`.
- [x] **Checkpoint 5b — UI polish: design-critique + visual identity.** Not originally planned as its own checkpoint — inserted after direct feedback that the shipped UI was "totally ugly." Two passes: (1) a `design-critique` audit, which surfaced a real bug hiding as a design choice (`globals.css`'s `--font-sans` was a circular self-reference, so the whole app silently rendered in the browser's default serif) plus touch-target sizes under WCAG minimums, bare-text loading states, and a too-subtle selected-answer highlight — all fixed and verified live. (2) A `frontend-design` visual-identity pass: a real palette (warm paper, deep teal accent, muted gold, 4 severity colors) replacing pure grayscale shadcn defaults, Fraunces headings paired with the existing Geist body font, a persistent `SiteHeader` for shared chrome, and a new signature element — `FairSpectrum`, a segmented tracker sized by each FAIR principle's real indicator count (4/3/1/4) — plus matching `PrincipleChip` badges on the review and report screens. Required a small backend addition (`principle_group` on `QuestionOut`/`FindingOut`). Self-review caught a real bug before merge: the tracker's fill math assumed FAIR groups were contiguous in display order, which they aren't (the flex-slot Findable question sits last); fixed and reverified live. **Immediate follow-up raised by the user after seeing this land** (not yet scoped into a checkpoint): the landing page still gives no context on what the tool is or which maturity model it's using; the question wizard doesn't show a worked example per indicator; there's no sense of "milestones" beyond the FAIR-spectrum bar; and what happens after the report (is it just text, or something more like a fillable worksheet / guided session) hasn't been designed at all. This is a content/IA-architecture question, not a color-and-type one — needs its own scoping pass before becoming a checkpoint.
- [x] **Checkpoint 5c — report screen rebuilt around structured, actionable findings; guided-remediation direction chosen.** User feedback on 5b went beyond color/type: unexplained jargon ("DOI" with no explanation), one dense paragraph per finding, passing indicators shown as bare titles with no explanation, small hard-to-read text. Asked to choose the "what happens after the report" direction from three options (downloadable artifact / action tracker / guided remediation sessions) — **chose guided remediation sessions**, the most ambitious. First step taken now: the remediation prompt (`remediation.jinja`, bumped to `fair-remediation-v2`) produces a structured `SUMMARY:`/`STEPS:` format instead of free prose, with an explicit rule that every acronym/tool name must be explained in plain words on first use. Every finding — including passing ones, not just gaps — now gets real LLM-generated content: a pass gets a short "why this is fine" note. Report screen rebuilt around a `FindingCard` component: one-line summary always visible, numbered steps behind a click-to-expand `Collapsible`. Two self-review bugs fixed before merge: a word-count floor that could reject valid short pass summaries, and a naive string search that could misparse a SUMMARY sentence containing the word "steps:". See `docs/DECISIONS.md` v13 for full detail. **Still open, not yet scoped:** landing-page context, per-question worked examples, and the actual guided-remediation-session flow (persisted per-finding status across visits) — this checkpoint only rebuilt the report's presentation/content model that flow will build on.
- [x] **Checkpoint 5d — landing-page context and per-question worked examples.** Closes two of 5c's three open items. Landing page rewritten with a plain-language legend for each FAIR letter, a 3-step "how this works" walkthrough, and a line naming the RDA FAIR Data Maturity Model and why this tool asks 12 of its 41 indicators. Every indicator gained a required `example` field — a concrete health-data/LMIC-grounded worked example shown directly under each question (not hidden behind a click), written to explain any technical term the moment it's first used rather than assume it. `dev.db` deleted and reseeded for the new column (no Alembic migration — still local-only SQLite with no real data). See `docs/DECISIONS.md` v14. **Still open:** the guided-remediation-session flow itself (persisted per-finding status, revisit-and-see-progress) — the one piece of the 5c direction not yet started, needs its own scoping pass before implementation.
- [x] **Checkpoint 5e — guided remediation, v0: revisit and re-score.** Closes the last item open since 5c. Scoped with the user first across 3 explicit forks (see `docs/DECISIONS.md` v15): "mark fixed" means re-answering the question (not a new status flag), progress tracking is single-assessment only for v0 (no cross-run history/trends yet), and revisiting reuses the existing single-question screen rather than a new inline editor. Report finding cards gained an "Update your answer" action; `PUT /answers/{indicator_id}` no longer blocks edits after completion; a new `_rescore_finding_and_refresh_report` re-scores and re-writes remediation for just the one changed indicator (one LLM call) and refreshes the cached report score — no new tables or columns needed. Two self-review bugs fixed before merge: an LLM-call exception that could turn a successful answer-save into a false 500, and a latent key-type mismatch (UUID vs `str(UUID)`) between two report-building functions that a new shared helper exposed. Verified live end to end: a licensing gap fixed via revisit correctly moved the score from 90.6 to 100 and reclassified the finding, with the other 11 findings' remediation left untouched. **Still open:** cross-assessment trend comparison (explicitly deferred, not forgotten) — revisit if the ACE pilot asks for it.
- [x] **Checkpoint 5f — FAIRification plan (synthesized, ordered guidance).** Prompted by synthesizing 3 eLwazi/ELIXIR FAIR-tooling reference documents against this tool's own design (see `docs/DECISIONS.md` v16). The RDA indicators measure *state*; ELIXIR's own FAIRification framework describes *action* (an 8-step template: get the data → model the domain → select identifiers → apply standards → choose vocabularies → transform for interoperability → host → share). Mapping each of the 12 findings onto one of the 8 steps is lossy (a few map cleanly, several don't map to any single step). Scoped instead as a new synthesized artifact: a single ordered plan, generated from *all* open findings together (not per-finding), each step referencing which specific findings it resolves — a new dedicated screen (`/assessments/{id}/plan`), not a report re-skin. Built (`docs/DECISIONS.md` v17): one LLM call per plan (not cached, unlike the report — cheap enough not to need it), defensive parsing that drops hallucinated indicator ids, the revisit flow generalized to return to either the report or the plan. Verified live: a 9-open-finding run produced 4 correctly-ordered steps covering exactly those 9 indicators, no more, no fewer, no hallucinations.
- [ ] **Checkpoint 6 — eval harness.** `golden_set.yaml` + automated LLM-judge scoring, formalizing what the Checkpoint 3 demo run validated informally. Prompt iterated until it passes.
- [ ] **Checkpoint 7 — deploy + dogfood.** Both services on Railway; a full self-run against real ACE data.
- [ ] **Checkpoint 8 — real ACE pilot.** A non-developer stakeholder runs it unassisted; feedback becomes new golden-set cases and indicator-subset corrections.

## Backlog — smaller improvements, not yet scheduled

Surfaced by the same reference-document synthesis as Checkpoint 5f, but small/independent enough not to need their own checkpoint. Pick up opportunistically.

- **Broaden repository recommendations in remediation prompts.** Currently every "assign a DOI" suggestion defaults to naming Zenodo alone. A comparison of 7 generalist repositories (Dataverse, Dryad, Figshare, Mendeley Data, OSF, Vivli, Zenodo) suggests a short decision rule instead: Zenodo (free, no institutional affiliation needed, up to 200GB/record) for general use; OSF (free, backed by a $250k long-term preservation continuity fund) as an alternative with a stronger durability guarantee; a university's own Dataverse where one exists (free, 1TB+); Vivli specifically for de-identified clinical trial data needing ethics-gated managed access. Bake this into `remediation.jinja`'s guidance rather than hardcoding one name.
- **Document this tool's positioning relative to F-UJI and the RDA FAIR Data Maturity Model** in `docs/DECISIONS.md` — F-UJI automates 16 of the same 41 RDA indicators but only the machine-readable ones (can a crawler resolve your DOI/metadata); it structurally cannot assess whether a data dictionary is any good or whether a non-technical lead understands what's being asked. Worth stating explicitly, both for this project's own record and in case the tool is ever shown to the eLwazi/ELIXIR community this research came from.
- **Evaluate the FAIR Cookbook** ([github.com/FAIRplus/the-fair-cookbook](https://github.com/FAIRplus/the-fair-cookbook)) — flagged by the user, not yet read. Comes with an explicit, real tension worth weighing deliberately rather than reflexively pulling in content from it: the user's own concern is that the FAIR-tooling ecosystem already has a proliferation problem — too many separate tools/frameworks/cookbooks for a non-technical lead to navigate — and every reference this tool absorbs risks making it feel like just one more entry in that pile rather than the single simple thing it's meant to be. Before pulling anything from the Cookbook in, the actual test should be: does this make the tool *more* self-contained and usable standalone, or does it just add another name/concept the user now has to know exists? Evaluate against that bar, not against "is this content good" alone.
- **Evaluate the FAIRplus Data-Maturity codebase** ([github.com/FAIRplus/Data-Maturity](https://github.com/FAIRplus/Data-Maturity)) — flagged by the user, not yet read. Likely the actual implementation behind the FAIR-DSM 5-level maturity model referenced in `docs/DECISIONS.md` v16 (levels 0-5, single-analyst local files up through enterprise semantic data governance). Worth the same proliferation-bar test as the Cookbook above before pulling anything in.

## Bigger directions to evaluate later — not scoped, not started

Distinct from the Backlog above: these would change what kind of tool this is, not just add a feature. Surfaced during the same research-synthesis conversation; deliberately not acted on yet.

- **"How does this all tie together?" is itself a real, validated need.** The user's own words, after attending real eLwazi/ELIXIR FAIR-training sessions: "it became a bit too much info for me." That's not a knowledge gap on the user's part — it's the same tool-proliferation problem named above, confirmed from the inside by someone who sat through the actual training this ecosystem offers. Directly validates that this tool's job includes synthesis (making the pieces cohere into one path), not just running a 12-question checklist. Worth treating as an explicit design question the next time the landing page or onboarding copy gets revisited: does a first-time user come away understanding how FAIR, F-UJI, the RDA model, and "FAIRification" as a process relate to each other — or just that they answered some questions and got a score?
- **An "over-the-shoulder" LLM mentor.** The user's proposal: instead of (or alongside) a fixed 12-question wizard, an LLM that watches over someone's actual FAIRification work in progress — the way a mentor would — drawing on the full body of FAIR reference material (RDA indicators, the FAIRification process/8-step template, F-UJI's machine checks, repository options, etc.) to guide anyone from newbie to expert to whatever level of FAIRness they're actually aiming for, not a fixed one-size-fits-all bar. This is a genuinely different product shape from what exists today — open-ended conversational guidance rather than a structured assessment flow — and would be a large scope decision, not an incremental feature. Keep for a dedicated scoping conversation, the same way Checkpoint 5f's guided-remediation direction got one before any code was written.

First pilot user: ACE's own data practices. No external dependency — already underway.

**Why the synthetic dataset checkpoint matters beyond just having a demo:** real institutional data — and especially anything OMOP CDM/health-record-shaped for the future v1 adapter — likely carries data-governance and consent restrictions that make sending it to *any* LLM (even an on-prem one) a real policy question, not just a technical one. A well-built synthetic dataset (varied sizes, formats, and plausible-but-fake governance gaps) lets the tool be built, tested, and demonstrated end-to-end without that question ever blocking progress — and gives a safe default for showing the tool to people outside ACE later. Building this early (Checkpoint 3, right after the indicator content) rather than bolting it on at the end.

## v1 — OMOP CDM data-quality adapter — **tracked, parked**

Same engine, pointed at OHDSI's Data Quality Dashboard output (3,300+ automated checks against an OMOP CDM database) instead of FAIR indicators — translating dense, informaticist-oriented DQD reports into plain-language findings for non-technical data staff.

- Status: **blocked**, not started. Waiting on: TASO (The AIDS Support Organisation, Uganda) data access, and the team's still-open decision on source system and ETL path to OMOP CDM.
- Explicitly out of scope for this adapter: building a new ETL engine. Existing OpenMRS→OMOP tools ([jayasanka-sack/openmrs-to-omop](https://github.com/jayasanka-sack/openmrs-to-omop), [Hephaestus](https://github.com/dermatologist/hephaestus)) and the pan-African INSPIRE datahub already cover that layer — this adapter starts downstream, at an existing OMOP CDM database.
- **Revisit trigger:** when TASO's OMOP CDM data (via whichever ETL path the team lands on) is actually queryable, and once v0's engine/adapter boundary has been validated by a real pilot.
- **Data-governance note carried over from v0's Checkpoint 3:** real TASO/OMOP data almost certainly needs a cleared policy path before it can touch any LLM, on-prem or not. Plan for this adapter to be built and demoed against synthetic OMOP-shaped Data Quality Dashboard output first, with real data substituted in only after that's explicitly cleared — not the other way around.
