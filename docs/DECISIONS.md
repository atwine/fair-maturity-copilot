# Decision log

How this project got scoped down from ten ideas to one, in order.

## v1 — ten ideas

Started broad: researched ACE's actual mandate (bioinformatics/data science, AMR, genomics — via ace.ac.ug), the existing open-source landscape (Sunbird AI for Luganda MT, Jacaranda's UlizaMama and Rwanda's Mbaza RBC for health chatbots, H3Africa/H3ABioNet for genomic infrastructure), and current funder priorities (Gates Foundation's EVAH initiative, Gates+OpenAI's Horizon 1000, the Gates/Google.org/Masakhane LINGUA Africa call) to produce ten scored candidate ideas. Full report: `background/v1-ten-ideas-for-ace.html`.

## v2 — four ideas

Cut based on direct feedback: the project owner is a developer and strategic/technical lead, not a bioinformatician, and wanted things he could personally build and debug — not hand off to deep domain specialists. Dropped AMR/WGS prediction, the federated genomic data-sharing toolkit, the pathogen genomics dashboard, and the pipeline-reproducibility tool on that basis. Also dropped a generic NCD chatbot and a crop-disease/Luganda voice tool as explicitly out of scope. Kept and refined: Luganda health-domain MT (flagship, since real assets already exist), a grant/manuscript-writing copilot, a FAIR data maturity tool, and a DHIS2 anomaly-detection tool. Full report: `background/v2-refined-ideas-for-ace.html`.

## v3 — two ideas, one engine

Further feedback: the grant-writing copilot was dropped on adoption-risk grounds (colleagues already have their own tools and wouldn't switch). The DHIS2 idea was replaced after new context surfaced — real, pending data access at TASO (The AIDS Support Organisation, Uganda), with an OMOP CDM/OHDSI architecture already being scoped by the team for federated analysis. Research showed a full OMOP ETL platform would duplicate existing work (INSPIRE datahub, several OpenMRS→OMOP ETL attempts), but that OHDSI's own Data Quality Dashboard output is dense and expert-oriented — the same gap shape as the FAIR maturity tool. Reframed both as one reusable engine (`intake → scoring → LLM remediation writer → report`) with a FAIR adapter and a future OMOP adapter. Full report: `background/v3-two-ideas-one-engine.html`.

## v4 — build order confirmed

FAIR adapter (idea #3) confirmed as the build-first project: no external data dependency, can start immediately, and validates the shared engine before the OMOP adapter depends on it. OMOP adapter (idea #4) tracked in `../ROADMAP.md` as parked, blocked on TASO's data access and ETL-path decision. Luganda MT (idea #1) confirmed strong but separately parked, pending the team's in-flight evaluation of ~10,000 curated translation pairs — it will live in its own repo when it starts, since it doesn't share the engine/adapter architecture.

## v5 — plan approved, engine scaffold built, process corrections

The v0 plan (indicator subset, data model, questionnaire flow, prompt design, milestones, eval approach) was produced via Plan Mode and approved. Two choices were made during planning that diverged from the plan's own default recommendations: Next.js was chosen over the plan's suggested server-rendered Jinja2+htmx frontend, and LLM serving was set to two verified on-prem OpenAI-compatible endpoints (local Ollama for dev, vLLM-hosted Llama 3.3 70B for pilot) rather than the plan's original hosted-third-party-API-for-dev suggestion — this removed any external data-exposure question entirely, since nothing leaves the local network at any stage.

Two process corrections landed alongside the first implementation checkpoint: the repo had been committed directly to a shared branch, against the standing branching convention — corrected by renaming `master` to `main` and moving to a feature-branch workflow with mandatory self-review before merge (see `README.md`). And the plan's day-based milestone estimates were replaced with checkpoint tracking in `ROADMAP.md`, since they assumed unassisted solo development and didn't match the actual pace of Claude-assisted implementation.

## v6 — branching corrected to the full three-tier structure

The v5 branching fix was incomplete: it moved work to a feature branch before merging into `main`, but skipped the staging tier and the PR-gated production step the user's CLAUDE.md actually specifies. Corrected to the literal three-tier structure: `feature/<name>` → `development` → `staging` → `main`, with `main` reachable only via a reviewed, explicitly-approved PR from `staging`. The already-merged backend scaffold on `main` stays as a one-time, explicitly-approved exception rather than a history rewrite — everything from this point on goes through the full structure. GitHub branch protection on `main` was attempted as a platform-enforced backstop and found unavailable on a private repo below GitHub Pro; noted as an option, not pursued. See `README.md`'s "Branching convention" for the canonical, current description.

## v7 — FAIR adapter content (Checkpoint 2), flex-slot resolved

The 12th "flex slot" indicator from the plan (a choice between F3-01M — metadata clearly identifies its dataset — and I3-01M — metadata links to related datasets) was resolved to **F3-01M**: it completes full coverage of the Findable principle (F1/F2/F3/F4 all represented), while I3-01M's cross-dataset linking is premature before ACE has more than a handful of catalogued datasets — consistent with why I3's other sub-indicators were already deferred in v5's indicator selection. Revisit after the first pilot if F3 turns out to be less useful in practice than I3 would have been.

Two real bugs were caught by actually running the code (not just review) while building this checkpoint: PyYAML's default "Norway problem" silently turned unquoted `yes`/`no` keys and values into Python booleans throughout `indicators.yaml`, and the seed script's success-message logging triggered a `DetachedInstanceError` by reading an ORM attribute after its session had closed. Both fixed; the seed script was then smoke-tested against a throwaway SQLite database (no Neon project provisioned yet) and confirmed idempotent on a second run. Self-review afterward caught two more issues: `indicators.yaml`'s anchor/alias reuse meant every indicator sharing the default rubric/options pointed at the *same* Python object rather than a copy (a latent shared-mutable-state risk), and the YAML file was being re-parsed from disk redundantly by three separate loader functions — both fixed in `content.py` (deep-copy per indicator, single cached parse).

## v8 — Checkpoint 3: synthetic demo datasets, remediation prompt pulled forward, LLM default switched to vLLM

Building the demo required a real remediation prompt template, originally scoped for a later checkpoint — pulled it forward rather than fake the demo output, since a demo that doesn't exercise the real generation path proves nothing. Four synthetic dataset fixtures were written (`backend/fixtures/synthetic_datasets.py`), deliberately spanning genomics, a flat CSV survey export, structured lab records, and an image archive, and deliberately spanning strong to weak FAIR practices — chosen so a demo run shows the tool's actual range, not one flattering score.

The first full run used the local Ollama endpoint (the plan's original dev default) and did not finish one dataset in 5 minutes. The user, who runs the actual GPU infrastructure, pointed out that vLLM is faster in practice on this hardware and is the only endpoint that will actually matter once this runs at ACE — the original plan's assumption ("small local model for fast dev iteration, avoid tying up the shared A100s") turned out to be wrong once tested against reality. Switched the default in `app/config.py` and `.env.example` to vLLM; Ollama remains available as an offline fallback only. Re-run against vLLM: all 4 datasets in ~150 seconds total, scores ranging 6.2–68.8/100.

That re-run also surfaced a real design gap in the remediation grounding check: a correct, appropriate "who to ask" response for a `dont_know` answer with a thin note ("This has never come up") was rejected for lacking word overlap with that note — but the prompt design deliberately asks for generic guidance in that case, so requiring overlap there was penalizing correct behavior. Fixed by exempting `dont_know` answers from the overlap check (word-count and jargon checks still apply), with a regression test added.

## v9 — Checkpoint 4: backend REST API, Adapter Protocol made to actually carry the report-generation contract

Building the report-generation route (`GET /assessments/{id}/report`) needed to call `render_remediation_prompt` and know a `prompt_version` — both of which only existed as FAIR-specific code (`app.adapters.fair.prompt`). Rather than let the API layer import that directly (breaking the standard-agnostic promise the engine/adapter split has made since v3), the `Adapter` Protocol itself was extended with `render_remediation_prompt` and `prompt_version`, and `app/adapters/registry.py` was added as the one place allowed to know concrete adapters exist. The API now depends only on the Protocol and the registry — adding the OMOP adapter later means one new registry entry, not API changes.

Mid-checkpoint, the vLLM endpoint went down for a period (server-side, confirmed by `/v1/models` itself timing out, not just generation) while the live report-generation tests were being written. Verified the new route logic was correct by falling back to Ollama rather than blocking on it; once vLLM came back, the full live suite was re-run against it and passed. Report generation is cached (one `Report` row per run) so repeat views never re-call the LLM — confirmed by asserting `generated_at` is identical across two consecutive `GET /report` calls in the test suite.

Self-review caught one real bug: report generation crashed with an unguarded `KeyError` (an opaque 500) if `Indicator` rows hadn't been seeded into the database yet — a genuinely likely setup-order mistake. Fixed with a clear error message naming `scripts/seed_indicators.py`, and a regression test using a deliberately unseeded database.

## v10 — Checkpoint 5: Next.js frontend, and a real race condition found by React itself

Scaffolded with `create-next-app` (Next.js 16, React 19, Tailwind v4) and `shadcn@latest`, which now builds on Base UI rather than Radix — different API in two ways worth remembering: polymorphic rendering uses a `render` prop (`<Button render={<Link .../>} nativeButton={false} />`), not `asChild`/`Slot`; and `next dev` auto-generates `AGENTS.md`/`CLAUDE.md` warning that this Next.js version postdates most training data and to check `node_modules/next/dist/docs/` before assuming API behavior — worth actually doing, not just noting, since the `params: Promise<{...}>` change in dynamic routes (must `await params`) is exactly the kind of thing that would otherwise silently misbehave.

The question wizard's edit-in-place flow (returning to a previously-answered question should show what was answered) needed the backend to expose full answer content, not just which indicators were answered — `AssessmentOut` gained an `answers: AnswerOut[]` field (`routes_assessment.py`'s `_to_out` rebuilt around it). Local component state for the question form is reset by remounting via `key={indicatorId}` rather than syncing through a `useEffect`, which is also what ESLint's `react-hooks/set-state-in-effect` rule (new in this React/eslint-config-next version) flagged when the first draft tried the effect-sync approach — the fix and the lint rule pointed at the same idiomatic answer independently.

The real finding: walking the completed flow in the browser produced a report claiming "8 of 24 indicators have something worth fixing" on a 12-indicator assessment, with every finding duplicated. React 19 Strict Mode double-invokes effects in development specifically to catch code that isn't safe to run twice — the report page's `GET /report` effect fired twice, and `_generate_report` had no protection against two concurrent callers both seeing "not generated yet" and both running a full LLM generation pass. This is a real production risk independent of Strict Mode (a double-click, a refresh mid-generation, two browser tabs), not just a dev-mode artifact.

Fixed at the database level, not just in application logic: unique constraints on `Answer`/`Finding` for `(run_id, indicator_id)` and on `Report.run_id`, so only one concurrent writer can ever succeed. The first fix attempt caught the constraint violation but returned immediately on conflict — wrong, because the losing request was giving up before the winner (still mid-LLM-call, easily 10-60+ seconds) had actually committed anything, itself producing a different error. Corrected to a bounded wait-and-retry: the loser polls for the winner's committed row instead of failing instantly. `routes_answers.py`'s upsert had the identical unprotected check-then-insert pattern and got the same fix pre-emptively, before it could produce the same bug under concurrent answer submission.

Verified three ways before trusting it: a direct-function test firing two threads at `_generate_report` against a shared engine, a real concurrent-HTTP test via `ThreadPoolExecutor` against a running server (this is what actually reproduced the "loser gives up too early" bug — the direct-function version was too fast to catch it), and a clean re-run of the full flow in the browser confirming no duplication and no console warnings. A related latent bug found while reasoning through the fix: `_load_report_out` picked an arbitrary `RemediationDraft` per finding when more than one existed (e.g. after using the regenerate endpoint), with no `ORDER BY` to guarantee the most recent one won — fixed alongside the race condition since it's the same code path.

## v11 — design-critique pass, and a font that was never actually rendering

Asked directly whether any remaining checkpoint covered visual design — none did (Checkpoints 6-8 are eval harness, deploy, and pilot, none of them UI work). Rather than let that gap surface later, ran the `design-critique` skill against all 4 live screens before continuing.

The critique's most consequential finding wasn't a taste judgment: `globals.css`'s `--font-sans: var(--font-sans)` is a circular self-reference (should have been `var(--font-geist-sans)`, the variable `layout.tsx` actually loads via `next/font/google`), so it resolved to nothing and the entire app was silently rendering in the browser's default serif font. This read, at a glance, as an intentional (if odd) typographic choice — it only surfaced as a bug once computed styles were checked directly (`getComputedStyle(document.body).fontFamily` returned `"Times New Roman"`). This is the kind of finding a design-critique pass catches that a code review wouldn't: nothing here throws an error or fails a type check, it just silently doesn't do what the code around it clearly intends.

Fixed alongside three other critique findings, all mechanical rather than matters of taste: button sizes computed to ~28-36px (under the 44px WCAG touch-target minimum) and got bumped across the whole size scale; the three data-fetching loading states were bare "Loading…"/"Generating…" text with no visual treatment, replaced with a shared `LoadingState` component (spinner + message); and the selected-answer highlight in the question wizard was a single-pixel border-color change, strengthened to a 2px border plus fill tint plus bold label.

Deliberately scoped this pass to fixes with an objectively correct answer — a broken font binding, a touch-target size below a written accessibility standard, a missing loading indicator. The remaining critique findings (no accent color anywhere, inconsistent card usage across screens, weak visual hierarchy on the report's score) are matters of design judgment, not correctness, and are being deferred to a follow-up pass with the `frontend-design` skill rather than decided unilaterally here.

## v12 — visual-identity pass: a real palette, a signature element, and a bug it exposed in itself

Follow-up to v11, using the `frontend-design` skill for the judgment-call findings that pass deliberately deferred: no real accent color, inconsistent `Card` usage, weak hierarchy on the report's score. Design plan: warm paper background (`#F2F1EA`) with a deep teal accent (`#1F5C54`, also driving shadcn's `--primary` so buttons/links/focus rings inherit it for free) and a muted gold second accent (`#B9862F`); Fraunces for headings paired with the already-loaded Geist for body text; a persistent `SiteHeader` so all 4 screens share chrome instead of floating alone in an unframed viewport. Four severity colors (pass/minor/major/unknown) were deliberately kept distinct from the brand teal/gold — a passing indicator shouldn't visually read as "the accent color."

The chosen signature element: `FairSpectrum`, a segmented progress tracker in the question wizard sized proportionally to each FAIR principle's real indicator count (4 Findable / 3 Accessible / 1 Interoperable / 4 Reusable), replacing the generic linear `<Progress>` bar. It reads at a glance that Interoperable is a single question, not a fourth of the assessment — which is true, and which an equal-width bar hides. Required a small backend addition: `principle_group` added to `QuestionOut` and `FindingOut` (`backend/app/api/schemas.py` and the two route files), since the frontend previously had no way to know which FAIR principle an indicator belonged to. A compact `PrincipleChip` variant of the same component now labels each row on the review screen and each finding on the report.

**A real bug this pass introduced, caught in self-review before merge, not by the user:** `FairSpectrum`'s first implementation computed each segment's "how much is filled" by assuming that principle's questions occupy one contiguous block in display order — a cumulative start-offset per group. The actual 12-question order isn't contiguous: the flex-slot Findable indicator (F3, see v7) sits last, after all four Reusable questions, specifically because it was added late to complete Findable's coverage rather than being grouped with the other three Findable questions at the front. Under the offset math, the Findable segment (4 questions, offset 0) read as 100% filled the moment the user reached question 5 — three questions before the true last Findable question (question 12) had even been asked, and it stayed stuck at 100% for the rest of the wizard. Fixed by counting each group's filled members by index directly (`principleGroups.filter((g, idx) => g === group && idx < completedThrough).length`) instead of assuming contiguity; reverified live by stepping to question 11 and confirming Findable correctly showed 75%, not 100%.

Score coloring on the report (`scoreTone()`) reuses the same three severity bands as findings do (pass ≥80 green, minor 50-79 amber, major <50 red) rather than inventing a fourth gradient — one semantic meaning for "this number is concerning," not two systems the reader has to learn separately.

## v13 — guided-remediation direction chosen; report screen rebuilt around structured, plain-language findings

User feedback on the freshly-merged visual-identity pass went well beyond color and type: the landing page gives no context on what the tool is or which model it follows, the wizard has no worked examples, there's no real sense of milestones, and — the sharpest point — the report itself was "just a list of cards" with small text, one dense paragraph per finding, passing indicators shown as bare titles with zero explanation, and unexplained jargon ("DOI") assumed as common knowledge. Asked directly to choose a direction for what happens after the report (a downloadable artifact, an action tracker with persistent status, or full guided remediation sessions) — the user chose **guided remediation sessions**, the most ambitious option. This entry covers the first concrete step toward that: rebuilding the report screen itself around structured, actionable, plain-language findings, since a coaching-flow UI would just be extending the same content model to a new screen — building it once, well, here first is not wasted work.

**Prompt contract changed** (`remediation.jinja`, `PROMPT_VERSION` bumped `fair-remediation-v1` → `v2`): every generation must now follow a fixed `SUMMARY: <sentence>` / `STEPS: 1. ... 2. ...` format instead of free-form prose, and a new explicit rule requires every acronym or tool name to be explained in plain words the moment it's first used ("a permanent web ID for your dataset (a DOI), which services like Zenodo can create for free" — not just "a DOI"). Verified live against real vLLM output: the model reliably produces the SUMMARY/STEPS structure and plain-language explanations without further prompting.

**Passing findings now get real content, not silence.** `_do_generate_report` previously skipped LLM generation entirely for `severity == "pass"` findings — they showed as a bare title in a plain list with nothing else. Every finding now gets a remediation call regardless of severity: a pass gets a short "why this is fine" SUMMARY with no STEPS section. This is the change with the biggest scope impact — report generation now makes up to 12 sequential LLM calls per run instead of as few as 2-3 for a mostly-clean dataset, meaningfully increasing generation latency and the live-test suite's runtime (31s → ~90-100s). Accepted as the right tradeoff: a 12-question tool with a ~1-minute report generation time is still reasonable, and "why this passed" is exactly the actionable information the user asked for.

**Engine/adapter seam change:** `Adapter.render_remediation_prompt` (`engine/ports.py`) gained a required `severity` parameter, since the FAIR adapter now needs it to choose the pass/gap/dont_know prompt branch. Every current and future adapter must implement this — a real (if small) breaking change to the Protocol, propagated to `routes_report.py`'s two call sites and `scripts/run_demo_assessment.py`.

**Frontend:** `frontend/lib/parse-remediation.ts` parses the SUMMARY:/STEPS: contract defensively (falls back to "whole text as summary, no steps" if the model doesn't comply, rather than showing nothing). The report screen now renders every finding through one `FindingCard` component (gap or pass) with a one-line summary always visible and a `Collapsible` (shadcn/Base UI, newly added) revealing numbered steps on click — addressing the "cards don't pop up, I have to squint" feedback directly. Body text bumped 14px → 16px throughout.

**Two bugs caught in self-review before merge, both fixed:** (1) the grounding check's word-count floor (8) could reject a genuinely good but short pass summary — loosened to 5. (2) `parseRemediation` originally searched for the literal substring `"STEPS:"` anywhere in the text, which would misfire and truncate the summary if the model's own SUMMARY sentence happened to contain that word sequence — anchored to a line-start match instead, matching the prompt's actual line-per-field output shape.

**Deliberately not done in this pass:** landing-page context, per-question worked examples, and the actual guided-remediation-session flow (persisted per-finding status, multi-visit progress) are all still open — this pass only rebuilt the report screen's presentation and content model, which the guided-session flow will build on rather than replace. See `ROADMAP.md`'s Checkpoint 5b note for the fuller scoping conversation still to be had.

## v14 — landing-page context and per-question worked examples

Follow-up to v13's two deferred items — the third (the guided-remediation-session flow itself) is still open, deliberately not started here; this closes the two smaller, well-defined pieces first.

**Landing page** (`app/page.tsx`) rewritten from a bare headline + button into: a legend explaining what each FAIR letter actually means in plain language (not just the word — a one-line question like "Can someone outside your team find out this dataset exists?" for Findable), a 3-step "how this works" walkthrough (answer 12 questions → get a score and report → follow concrete next steps), and a closing line naming the Research Data Alliance's FAIR Data Maturity Model and explaining why this tool asks 12 of its 41 indicators rather than the full set. Answers the user's specific complaint that arriving at the tool gave "no context... what exactly is happening."

**Worked examples** added as a new `example` field on every indicator — a required `Indicator` model column (new, no Alembic migration since the dev database is still local SQLite with no real data in it; `dev.db` was deleted and reseeded rather than migrated). Each of the 12 examples is grounded in a concrete health-data/LMIC research scenario matching the tool's actual audience (a TB genomics dataset uploaded to Zenodo, a REDCap-collected survey, a WHO ethics-approval process), contrasting a "this counts" case against a "this doesn't" case where that clarifies the boundary. Rendered directly under each question in the wizard, always visible — not hidden behind the existing "Why this matters" toggle, since an example is exactly the kind of content someone with no data-management background needs before they can even answer, not optional background reading.

Both changes directly answer the user's most pointed feedback in this stretch: "you can say 'DOI' and assume whoever reads that acronym knows what it means... otherwise people will not be able to act on it, even after all the effort we have put in." The examples are written to name a technical term once, in context, without assuming the reader already knows it — the same plain-language discipline v13 already applied to the LLM-generated remediation text, now applied to the static question content too.

**Deliberately not done here:** the guided-remediation-session flow itself — persisted per-finding status, revisiting an assessment over time and seeing progress — remains the one piece of the direction chosen in v13 that hasn't been started. It's the largest remaining piece and still needs its own scoping pass (data model for status, what "resolved" means, whether/how a re-assessment compares against a prior one) before implementation.

## v15 — guided-remediation session, scoped down and built: revisit, re-score, no new data model

Before building anything, scoped the v13/v14-deferred guided-remediation-session flow with the user across three explicit forks, each resolved to the smaller/cheaper option:

1. **What does "mark this fixed" mean?** Re-answer the question, not a separate status flag. A `Finding`'s `severity` is already derived live from its `Answer` — adding a parallel "resolved" boolean would create two sources of truth (the answer says No, the flag says done) that could drift apart. Re-answering means the score, severity, and "Looks good" grouping all stay correct automatically, for free.
2. **Cross-assessment progress tracking, or single-assessment only?** Single-assessment only for v0. Watching one assessment's own score climb as its answers are revisited delivers the "come back and see improvement" feeling the user described, without a new `Subject`/`Dataset` entity linking multiple runs, a history dashboard, or trend charts — real scope, deferred until the ACE pilot actually asks for it.
3. **How does someone revisit one indicator?** Reuse the existing single-question screen (`QuestionForm`), not a new inline-edit UI on the report cards. `QuestionForm` already existed and worked; building a second, parallel answer-editing surface would mean keeping two UIs in sync for no real UX gain.

**What this meant technically:** `PUT /assessments/{id}/answers/{indicator_id}` no longer rejects edits once a run is `completed` (`routes_answers.py`) — that block existed only because the original flow was strictly linear; the report's own generate-once-cache-forever design was the actual reason edits couldn't safely happen after completion, not a deliberate immutability guarantee. A new `_rescore_finding_and_refresh_report` (`routes_report.py`) runs after a completed-run answer changes: re-scores the one affected `Finding`, re-writes its remediation (one LLM call, not twelve), recomputes the composite score from all current findings, and updates the cached `Report` row in place. No new tables, no new columns — this is the payoff of choice #1 above: the existing scoring/remediation machinery already does the right thing once triggered on the right event.

**Frontend:** report finding cards gained an "Update your answer" action linking to `/assessments/{id}/question/{indicatorId}?from=report`. The question page detects `?from=report` and switches into a lighter "revisit" mode: no wizard chrome (no "Question X of 12," no `FairSpectrum` tracker — those describe progress through the original 12-question flow, meaningless for editing one answer in isolation), a "Cancel" link back to the report instead of "Back," and "Save and return to report" instead of "Next" — which navigates straight back to the report on success rather than advancing to the next question.

**Two bugs caught in self-review before merge:**
1. `_rescore_finding_and_refresh_report` originally let the remediation LLM call's exception propagate all the way up through the answer-PUT endpoint — meaning a network hiccup during regeneration would return a 500 to the client even though their answer had already been saved and committed. Wrapped the regeneration step in a narrow try/except: the severity update (no LLM involved) always commits and is reflected in the score; only the remediation *text* is left showing the previous draft if the LLM call fails, recoverable via a regenerate or another revisit.
2. Extracting a shared `_latest_remediation_by_finding_id` helper (used by both report loading and the new rescore path) surfaced a latent key-type mismatch that existed even before this pass: `build_report_markdown` (`engine/report.py`) looks up remediation drafts by `str(finding.id)`, but the original `_load_report_out` dict was keyed by the raw `Finding.id` UUID object. The two functions had never been called with the same dict before, so the mismatch was invisible — it would have silently produced remediation-less markdown the moment anything reused that dict for both purposes, which is exactly what this pass did. Fixed by standardizing the shared helper on string keys.

**Operational note, third time this has bitten a session in this repo:** `uvicorn --reload` does not reliably pick up file changes in this OneDrive-synced working directory — confirmed again here (edited `routes_answers.py`, `--reload` never logged a restart, the server kept serving the pre-edit code with the old "answers can no longer be edited" 400 for several verification attempts). Manually killing and restarting the backend process after every backend edit is the only reliable option in this environment; don't trust `--reload` here even when it's passed.

**Verified:** `tsc --noEmit`, `eslint`, and a full `next build` (checking specifically that the new `useSearchParams()` usage doesn't hit Next.js's static-rendering/Suspense requirement — it doesn't, since this route was already dynamic) all clean. 35 backend tests passing, including a new live test against real vLLM (`test_revisiting_an_answer_rescoes_and_refreshes_the_report`) asserting the revisited finding's severity/remediation/score all update correctly *and* that the other 11 findings' remediation text is untouched — proving this is a targeted single-indicator update, not a disguised full regeneration. Walked the full flow live in the browser end to end: opened a completed report showing a licensing gap (score 90.6), clicked "Update your answer," changed the answer, was returned to the report automatically, and saw the score at 100 with the finding correctly reclassified as "Looks good."

## v16 — synthesizing eLwazi/ELIXIR FAIR-tooling reference material against this tool's own design

The user pointed at three reference documents used at eLwazi (the DS-I Africa Open Data Science Platform, NIH-funded, hosted at UCT — the same network H3ABioNet sits in) to check whether this tool's approach is actually sound, and to learn how to make it more useful. Read all three plus targeted web research on the surrounding ecosystem (eLwazi's own FAIR guidance page, F-UJI, the RDA FAIR Data Maturity Model's own documentation).

**The verdict: the foundation holds, one layer is genuinely missing.** eLwazi has no bespoke African FAIR framework of its own — its own user-support page points researchers to the same global tooling this research covered (the FAIRplus Dataset Maturity Model via RDMkit, the FAIR Cookbook, ELIXIR's RDMkit). The "WEI-FAIRification-Framework-Africa" deck, despite its filename, turned out to be standard FAIRplus/ELIXIR training material delivered at the Cape Town venue (eLwazi ODSP 2026 Data Jamboree) by EMBL-EBI/ELIXIR Switzerland/ELIXIR Luxembourg speakers — not an Africa-specific adaptation. Useful to know: there's no competing regional standard this tool is out of step with.

**Validated, specifically:**
- The RDA FAIR Data Maturity Model (this tool's base) is exactly what eLwazi's own guidance points to, and it's the same base F-UJI (the field's automated FAIR checker) partially automates — F-UJI covers 16 of the same 41 indicators, but only the *machine-readable* ones (can a crawler resolve a DOI, parse metadata). It structurally cannot assess whether a data dictionary is any good, or whether a non-technical lead even understands what's being asked of them. This tool's human self-report plus LLM-mediated plain-language remediation is the layer F-UJI admits it can't reach — complementary, not redundant.
- "FAIR as a state, not an alphabet" (a real distinction from the reference deck: don't let someone fixate on four independent F/A/I/R scores when reuse, not per-letter completeness, is the actual goal) is a principle this tool already followed without knowing it had a name — one composite score across all 12 weighted indicators, never four separate per-letter scores.

**The gap, and what it sharpens:** the FAIRification framework's real value isn't its assessment step — it's the process that's supposed to follow: a Goal statement (what/why/how/what "done" looks like) → Project Examination → an 8-step execution template (get the data → model the domain → select an identifier scheme → apply data standards → choose vocabularies → transform for interoperability → host → share) → review. This tool currently stops at the report — remediation *text* per finding, but nothing sequences "do this first, then this."

**Scoped with the user before building anything (Checkpoint 5f):** mapping each of the 12 RDA indicators onto one of the 8 execution steps 1:1 was considered and rejected — the RDA indicators measure *state*, the 8-step template describes *action*, and a few indicators (F2 "enough metadata," F4 "discoverable") are outcomes of doing several steps well, not one step each; forcing a clean per-finding tag would mean mis-tagging some and orphaning others. Instead: a new synthesized artifact — one ordered plan, generated by looking at *all* currently-open findings together (not per-finding), each step in the sequence naming which specific findings it resolves. Two decisions locked before implementation: (1) it lives on its own new screen, not folded into the report, since the report's job is "here's your score" and the plan's job is "here's what to do about it, in order" — different enough to earn separate space; (2) it's built now, before Checkpoints 6/7 (eval harness, deploy) — continuing to shape what the tool actually does before locking in an evaluation baseline against it, the same sequencing this whole session has followed since the "totally ugly" feedback that started it.

**Filed to the backlog, not built now (small, independent, no scoping needed):** broadening remediation prompts' repository guidance beyond a bare "Zenodo" mention — a 7-repository comparison chart (Dataverse, Dryad, Figshare, Mendeley Data, OSF, Vivli, Zenodo) surfaced concrete numbers worth using (Zenodo: free, no affiliation required, up to 200GB/record; OSF: free, backed by a $250k long-term-preservation continuity fund; institutional Dataverse: free, 1TB+; Vivli: purpose-built for de-identified clinical trial data needing ethics-gated managed access) — and a documentation task to explicitly position this tool relative to F-UJI/RDA-DMM for the record. See `ROADMAP.md`'s Backlog section.

**Two more resources and a bigger idea, surfaced mid-build, filed rather than acted on:** the user pointed at the FAIRplus Data-Maturity GitHub repo (likely FAIR-DSM's actual implementation) and the FAIR Cookbook, both parked in `ROADMAP.md`'s Backlog under the same "does this make the tool more self-contained, or just add one more name to know" bar as the reference documents above. More significantly, the user named the exact failure mode this synthesis was trying to guard against, from direct experience: "I attended some sessions but it became a bit too much info for me" — confirming the tool-proliferation concern from the inside, by someone who sat through real eLwazi/ELIXIR training. They also proposed a materially different product shape: an "over-the-shoulder" LLM mentor that watches someone's actual FAIRification work and guides them conversationally, digesting the full body of reference material, rather than running a fixed 12-question checklist. Both filed under a new "Bigger directions to evaluate later" section in `ROADMAP.md` — explicitly not scoped or started, since a shape change like the mentor idea deserves its own dedicated scoping conversation, not a decision folded into this one.

## v17 — FAIRification plan built: one synthesized ordered walkthrough per run

Implementation of the direction scoped in v16. `app/adapters/fair/plan.py` renders a new prompt (`fairification_plan.jinja`) against *all* of a run's open findings in a single call, asking for a `GOAL:`/`STEP:`/`ADDRESSES:`/`DETAIL:` structured response — the same defensive-parsing philosophy as `remediation.jinja`'s `SUMMARY:`/`STEPS:` contract (v13), extended here to also validate that every id in `ADDRESSES` actually belongs to the set of open findings passed in, silently dropping anything hallucinated (and dropping a step entirely if every id it named turns out to be invalid, rather than showing an orphaned, unlinked step). All-passing runs short-circuit before ever calling the LLM.

`GET /assessments/{id}/plan` (`routes_plan.py`) is deliberately **not cached** — the report's generate-once-cache-forever design (and the whole invalidate-on-revisit machinery built for it in v15) exists because report generation is up to 12 sequential LLM calls; the plan is exactly one call regardless of how many findings are open, so regenerating fresh on every visit is simpler than replicating that caching complexity for a call cheap enough not to need it.

**A bug caught in self-review before merge:** an empty `Plan.steps` list meant two different things depending on how it got there, and the code didn't distinguish them. "No open findings" (the deliberate short-circuit, returned before ever calling the LLM) and "the model's response failed to parse into any usable steps" (a real failure — malformed output, or every `ADDRESSES` line hallucinated and dropped) both produced the same empty-steps `Plan`, which the frontend would render identically as "Nothing left to plan for — every indicator already checked out clean." For a run that actually had open gaps, that's a false "you're done" message sitting directly under a goal sentence describing work still needed. Fixed by raising a dedicated `PlanGenerationFailed` when open findings exist but parsing yields zero steps, caught in `routes_plan.py` as a 503 ("try again in a moment") rather than silently returning a misleading clean plan. A new regression test mocks the LLM call to return unparseable text and asserts the exception fires.

Verified live end to end against real vLLM output: a 9-open-finding run correctly produced 4 ordered steps (documentation → standards → hosting/discoverability → access/persistence) covering exactly those 9 indicator ids, no more, no fewer, no hallucinated ones. Followed a step's indicator pill through the generalized revisit flow and confirmed it returns to the plan, not the report.

**An unrelated but real bug hit during this verification, worth recording:** the frontend Next.js dev server (Turbopack) had been silently failing for several minutes before this feature was even touched — `.next/dev/logs/next-development.log` showed repeated "Jest worker encountered 2 child process exceptions" and `write EPIPE` errors going back well before this session's edits, with several orphaned near-zero-memory `node.exe` worker processes still running after the main dev server process was killed. Not caused by this feature's code (confirmed clean via `tsc`/`eslint` before ever touching the browser) — this looks like the same class of problem as the backend's `--reload` unreliability in this OneDrive-synced directory, just manifesting as compile-worker crashes instead of a stale-code server. Fixed by killing the main process *and* every orphaned worker process individually, deleting `.next/` entirely, and restarting clean. **If the frontend dev server starts erroring in ways that don't match the code (blank pages, `_error` responses, stack traces mentioning "Jest worker"), check `.next/dev/logs/next-development.log` before assuming it's a real bug — kill any orphaned `node.exe` processes and delete `.next/` before restarting.**
